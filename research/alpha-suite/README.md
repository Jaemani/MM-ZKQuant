# 외부·커스텀 데이터 알파 전략 7종과 플랫폼 수용 판정

작성: 2026-09-17. 목적은 실제 제작자가 가져올 법한 전략을 구체화해 **우리 플랫폼이 무엇을 받아야 하는지** 확인하는 것이다. 모두 새로 작성한 연구 후보이며 검증된 수익 전략을 가져온 것이 아니다.

**결론: 현 설계에 가장 잘 맞는 것은 저빈도 현물 전략 + 사전 확정된 외부 피처 입력이다. 커스텀 데이터도 계산은 가능하지만, 창작자가 매번 임의 점수를 넣을 수 있으면 ‘전략 고정’의 의미가 약해진다. 데이터 생성 규칙 또는 독립 공급자까지 고정해야 한다.**

이 작업 폴더에는 [플랫폼 설계 근거](../technical-evidence.md), [기존 어댑터 실험](../adapter-evidence.md)이 있다. 업로드 API, 등록 SDK, 실제 DSL, zkVM guest, 실행 서버는 발견되지 않았다. 따라서 **아래 7종 모두 실제 업로드·등록 성공은 미확인**이다. ‘1차 후보’는 기존 문서의 제한된 현물 MVP에 대한 설계 판단이다.

## 공통 실행 계약

- 코드: [strategies.py](strategies.py). 표준 Python만 사용하는 결정 함수 7개. 입력은 최대 512개 정수 피처, 출력은 NAV 대비 목표 명목 비중이다. 외부 HTTP는 결정 함수 밖에서 수행한다. 상태를 누적하지 않는 목표 비중 전략이라 신호가 꺼지면 목표 0을 출력한다.
- `bps`: 1 = 0.01%, 10,000 = 100%. `ppm`: 1 = 0.0001%. 점수 `milli`: 1,000 = 1.0. 음수 나눗셈은 floor로 정한다. 실제 정수 입력의 허용 범위는 `FEATURES`에 있다. Python host 실행이며 zkVM 정수 타입·회로 구현 검증은 아니다.
- 가격 피처는 확정 4h 캔들 기준 `trend_30d_bps = floor((close / close_180bars_ago - 1) × 10000)`, `return_1d_bps`는 6 bars 전 대비다. 연속 캔들 검증·자산 매핑·거래소 가격 정의는 production 어댑터가 강제해야 한다. 예제 재생은 이미 저장된 BTCUSDT 2024년 11~12월 가격을 사용한다.
- 행은 `name, asset, value, event_at, available_at, source, revision`. `asset`은 적용 대상이며 시장 전체 피처도 전략의 BTC 적용으로 표시한다. 원천 자산 universe와 계산법은 별도 데이터 계약에 결박해야 한다. `source`는 허용 어댑터 이름일 뿐 서명이 아니다. 입력 파일 작성자가 이 문자열을 맞출 수 있으므로 이것만으로 인증이 되지 않는다.
- `event_at ≤ available_at ≤ cutoff`, 최대 유효 기간, 자산·공급자·수치 범위, 중복을 검사한다. 미래 공개 revision은 과거 결정에 쓰지 않는다. 미래 이벤트 자체를 담는 언락 피처의 `event_at`은 **일정 스냅샷 기준 시각**이며 미래 언락 날짜가 아니다.
- 데이터 누락·노후화는 `DATA_BLOCKED`, `targets_bps=null`이다. 이것은 정상 HOLD나 청산 성공이 아니다. 실제 보유 포지션의 비상 축소·헤지 유지·주문 취소는 별도 공개 장애 정책과 executor가 수행해야 한다.
- 이 파일에는 actual fills, 계정 NAV, 중복 epoch/replay 방지, 주문 TTL, 잔고·증거금, 수수료 정산, 상태 commitment, 공급자 서명, proof가 없다. target 0도 실제 체결 전에는 포지션 0이 아니다.

## 1. 펀딩 과열 회피 추세

**가설:** 상승 추세는 따라가되 레버리지 롱이 비싸게 몰린 구간은 피한다. 펀딩이 높다고 즉시 숏을 치는 전략보다 현물 MVP에서 다루기 쉽다.

**데이터·전처리:** BTCUSDT 현물 종가, Binance USD-M BTCUSDT의 최근 확정 펀딩. `funding_24h_ppm`은 최근 24시간 정산 rate 합 × 1e6을 floor한다. 예제는 **8시간 간격 3회**만 허용한다. 펀딩 간격이 변경되면 해당 어댑터 버전을 거부하거나 새 interval-aware 버전을 등록한다. 미래 예상 펀딩과 이미 확정된 펀딩을 섞지 않는다.

**규칙:** 4시간마다, 30일 수익률 > 0이고 24시간 펀딩 합 ≤ 300ppm(3bps)이면 BTC 50%, 아니면 0%. 남은 NAV는 현금이다. threshold를 벗어나면 다음 허용 실행 창에서 축소한다. 직접 현물 매수이므로 펀딩을 받거나 내는 전략은 아니다.

**평가:** 같은 50% 가격 추세 전략에 비해 펀딩 필터가 비용 후 수익·낙폭·회전율을 개선하는지 비교한다. 펀딩은 가격 추세와 겹칠 수 있고 과열장이 오래 지속되면 상승을 놓친다. 거래 수수료·왕복 슬리피지·현금 보유 기회비용을 넣는다.

**플랫폼 요구:** 가격 외에 funding schema, 확정 시점, 간격, 원천·snapshot root만 추가하면 결정부는 작다. ZK 안에서 HTTP를 호출할 이유가 없다. 실제 proof 시간은 미측정이다.

## 2. 극단 공포 후 가격 반등

**가설:** 극단 공포만 보고 매수하지 않고 가격 반등을 확인해 단기 과매도 회복을 노린다.

**규칙:** 하루 1회, Fear & Greed ≤ 25, 1일 BTC 수익률 ≥ 1%, 30일 수익률 ≥ -15%를 모두 만족하면 BTC 25%, 그 외 0%. 보유 중에도 다음 일별 결정에 조건이 사라지면 청산 목표를 낸다. 임의 재량으로 ‘회복할 때까지 보유’하지 않는다. 코드 자체는 스케줄러가 없으며 아래 4h 재생은 입력 수용 시험이다.

**데이터:** [Alternative.me](https://alternative.me/crypto/fear-and-greed-index/) 원자료. 지수 timestamp와 정확한 최초 발표 시각은 다르다. UI에서 데이터 표시 시 가까이에 Alternative.me 출처를 명시한다. 지수는 가격·거래량을 포함하므로 독립 알파라고 가정하지 않는다.

**평가·실패:** 저가 매수 후 추가 급락, 드문 진입, 하루 만의 조건 이탈로 회전 비용이 커질 수 있다. 지수 없는 동일 가격 조건과 비교하고, bearish/bullish 기간을 나눠 평가한다. 예제 실데이터 기간에는 진입이 0회였으며, 수익성을 입증하지 못한다.

## 3. 스테이블코인 공급 확장 + 추세

**가설:** USD 연동 스테이블 공급 증가가 crypto 위험자산 수요의 조건이 될 수 있다. 공급 증가는 대기 자금일 수도 있어 가격 확인을 붙인다.

**데이터·전처리:** DefiLlama `totalCirculating.peggedUSD`의 7일 변화율 bps. 서로 다른 통화나 브리지 중복을 단순 합산하지 않는다. 원천의 자산 포함 규칙을 고정한다. 디페그 피처는 사전 정한 USDT·USDC의 USD 기준 확정 가격에 대해 `max(abs(price/1USD - 1)) × 10000`을 보수적으로 올림한다. 7일 전 관측치가 없으면 보간하지 않는다.

**규칙:** 하루 1회, 공급 7일 증가 ≥ 0.5%, 디페그 ≤ 0.5%, BTC 30일 추세 > 0이면 BTC 50%; 아니면 0%. 디페그 가격은 1시간 이내, 공급 스냅샷은 2일 이내로 제한한다.

**평가·실패:** 발행이 매수를 뜻하지 않으며 커버리지 변경이 가짜 공급 증가를 만들 수 있다. 공급량 필터 없는 추세 전략과 비교한다. 디페그 때 목표 현금의 자산도 명시해야 한다. 매도 후 동일하게 디페그된 코인을 보유하면 피난 효과가 없다. 이 예제는 현금 자산을 집행하지 않는다.

**준비 수준:** 공급량 API 가용성은 확인했다. 실제 공급량·디페그·가격을 결합한 historical replay는 아직 없다. raw-to-feature 어댑터가 필요한 수용 시험 후보이다.

## 4. 자체 거래소 주소 라벨의 순유출

**가설:** 거래소에서 외부 지갑으로 나가는 BTC가 비정상적으로 많고 가격 추세가 양수면 즉시 매도 가능한 공급이 줄었을 수 있다.

**커스텀 정의:** 네이티브 Bitcoin 전송과 사전 등록한 거래소 주소 라벨을 사용한다. 내부 이동·동일 소유자 이동을 제외하고 일별 `netflow = external_in - external_out`을 만든다. 당일 값을 포함하지 않는 과거 90개 완결 일자의 median/MAD로 `z = (netflow - median) / (1.4826 × MAD)`를 계산, ×1000 후 floor한다. MAD=0·90일 부족은 missing이다. 계산 규칙과 반올림을 피처 버전에 고정한다.

`flow_coverage_bps`는 실제 모든 거래소 주소를 얼마나 아는지가 아니다. 사전 고정된 추적 대상·블록 범위에서 수집 완료한 데이터의 비율이다. 최소 분모, 누락 블록·공급자 장애를 원자료와 함께 기록한다. 창작자가 임의로 100%를 쓰지 못하도록 파이프라인을 인증해야 한다.

**규칙:** 하루 1회, z ≤ -1.5, 수집 coverage ≥ 90%, BTC 30일 추세 > 0이면 BTC 35%; 아니면 0%. Dune Ethereum/WBTC 데이터로 대체할 경우 별도의 WBTC proxy 전략으로 이름·버전을 바꾼다.

**평가·실패:** 주소 신규 발견을 과거에 소급하면 lookahead가 생긴다. 당시 알려진 라벨만 사용한다. 커스터디 재편·거래소 준비금 이동이 매도 압력과 무관한 대규모 순유출을 만든다. raw netflow와 함께 이벤트를 감사하고 가격 단독 대비를 본다.

**플랫폼 판정:** 커스텀 피처의 수치 비교는 쉽다. 그러나 외부 score만 ZK 입력으로 받으면 **라벨·SQL·정규화의 정확성을 증명한 것이 아니다**. 독립 공급자 attestation 또는 고정 파이프라인 실행 증명이 필요하다. 이 작업에는 실제 지갑 데이터셋 대신 명시적 합성 JSON을 넣었다.

## 5. 알려진 언락 회피형 SOL 추세

**가설:** 추세 추종 중 큰 예정 공급 이벤트에 노출되는 시간을 줄인다. 언락=매도를 가정하지 않고 롱 위험을 줄이는 필터로 쓴다.

**커스텀 정의:** 판단 시각 전에 알려진 일정의 향후 7일 팀·투자자 cliff + linear emission 수량을 합쳐, 당시 알려진 유통량으로 나눈 값 ×10000을 보수적으로 올림한다. 중복 이벤트·vesting 계약을 제거한다. `unlock_7d_float_bps=0`은 **커버리지 완전, 일정 없음**을 확인한 경우만 유효하다. API 응답 실패를 0으로 바꾸지 않는다.

**규칙:** 하루 1회, SOL 30일 수익률 > 0이고 7일 예정 공급 < 유통량의 1%이면 SOL 25%; 그 외 0%. 7일 창에서 이벤트가 빠지고 다음 정상 입력이 오면 자동 재평가한다. 일정 변경은 새 revision으로 기록한다.

**평가·실패:** 시장이 이미 반영한 일정, OTC 매도, 실제 유통량 정의, 발표 지연에 민감하다. SOL 선정은 플랫폼 입력·종목 확장 시험을 위한 예시이며 큰 언락이 자주 존재한다는 주장이 아니다. 실제 일정 밀도를 조사한 뒤 사전 고정 universe를 정한다.

**플랫폼 판정:** Tokenomist의 인증 데이터와 과거 일정 버전은 확보하지 않았다. 공식 발행사 공지의 최초 수신 기록도 대안이다. 현재 수정된 미래 일정을 과거에 소급한 백테스트는 받지 않는다. SOL 매매 venue·유동성도 별도 수용 조건이다.

## 6. 고정 뉴스 모델의 긍정 이벤트

**가설:** BTC 관련 신규 긍정 뉴스가 쌓였으나 가격이 아직 크게 뛰지 않은 구간에 작게 노출한다.

**커스텀 정의:** 허용된 뉴스/RSS의 최근 6시간 최초 수신 문서만 사용한다. 동일 기사·신디케이션을 고정 hash/규칙으로 중복 제거한다. 사전 고정 종목 매핑 후 문서별 `(p_positive - p_negative)` 평균 ×1000을 floor하여 `news_score_milli`, 고유 문서 수를 `news_count`로 만든다. 모델·tokenizer·weights·전처리·문서 수정 버전을 고정한다. 모델 출력 확률의 quantization 정책도 필요하다.

**규칙:** 4시간마다, 점수 ≥ 0.35, 문서 ≥ 5개, BTC 1일 수익률이 -5%~+8%이면 BTC 20%; 아니면 0%. 신호가 계속되면 재평가마다 보유를 유지하며 ‘최대 6시간 보유’ 규칙은 아니다.

**평가·실패:** 광고·복제 기사·자산 오분류, 영어 금융 모델의 crypto 부적합성, 이미 가격에 반영된 뉴스가 문제다. 가격 단독·기사 수 단독·셔플한 점수와 비교한다. 모델 학습 종료 시점 이전의 과거 성과를 당시 실행 가능했다고 주장하지 않는다.

**플랫폼 판정:** 코드가 실행하는 것은 **점수를 받은 뒤의 결정부뿐**이다. FinBERT 자체를 실행하거나 ZK로 추론을 증명하지 않았다. 독립 점수 공급자 신뢰형은 조건부 후보, 전체 모델 inference의 ZK 지원은 현재 미확인이다. 외부 LLM에 매번 자유 질의를 보내는 전략은 고정 deterministic artifact로 취급할 수 없다.

## 7. 비용 차감 현물–무기한 펀딩 캐리

**가설:** 양의 펀딩을 받는 short perp와 같은 BTC 수량의 long spot을 조합하되 예상 수입이 비용·위험 여유를 넘을 때만 진입한다. ‘무위험 차익’은 아니다.

**커스텀 정의:** 최근 9회의 확정 8h 펀딩 rate를 정렬하고 하위 25%의 nearest-rank 값(세 번째 값)을 보수적인 다음 72h의 회당 예측으로 사용, ×9×10000 후 floor한다. 정산 간격이 다르면 해당 버전에서는 missing이다. 예측은 확정 수입이 아니다. 비용 피처는 양 다리 진입+청산 수수료·슬리피지·차입/자금비용·베이시스 이동 예산을 **한쪽 헤지 명목금액 기준 bps**로 합쳐 올림한다.

**규칙:** 시간당 1회, 예상 72h 수입 − 총비용 ≥ 15bps, 현물 대비 perp 절대 베이시스 ≤ 50bps, 증거금 여유 ≥ 30%이면 현물 +25%, perp -25%; 아니면 양쪽 0%. `margin_buffer_bps`는 `(margin equity - maintenance requirement) / margin equity ×10000`의 floor이며 equity≤0은 missing이다. NAV 비중이 같은 것은 가격 차이 때문에 정확한 수량 중립과 다를 수 있어 executor가 동일 BTC 수량으로 조정해야 한다.

**평가·실패:** 펀딩 반전, basis 확대, 일방 체결, 청산·ADL, 거래소 출금 장애가 남는다. 실제 funding ledger·mark-to-market·수수료로 NAV를 계산해야 한다. 두 다리의 합산 gross 목표는 NAV 50%지만 증거금과 현물 자금 배치는 별도다.

**플랫폼 판정:** 단일 현물 one-shot executor로는 수용하지 않는다. 헤지 상태 머신, partial fills, 수량 오차 상한, timeout 후 unwind, margin oracle, funding 정산, venue별 exposure limit이 있어야 한다. 코드의 두 target 출력을 ‘원자적으로 체결된 헤지’라고 해석하면 안 된다.

## 실제 실행 결과와 재현

```bash
rtk proxy python3 -m unittest discover -s research/alpha-suite -v
rtk proxy python3 research/alpha-suite/replay.py
rtk proxy python3 research/alpha-suite/run.py research/alpha-suite/data/custom-input.example.json
```

별도 패키지 설치 없이 실행한다. `replay.py`는 최초 실행 때 공개 데이터를 다운로드하고 이후 저장된 파일과 SHA-256을 검사해 재사용한다. [results.json](results.json)에 코드 hash와 입력 가격 hash, 합성 예제, 신호 수를 기록한다. [개별 결정](data/archival-decisions.json)에는 cutoff·입력·결과를 모두 저장했다. 새 다운로드는 스냅샷을 별도 보관한 뒤 수행해야 한다.

| 2024-12 4h 입력 시험, 전략별 186 epochs | 양의 목표 | 0 목표 | DATA_BLOCKED |
|---|---:|---:|---:|
| 펀딩 과열 회피 추세 | 83 | 100 | 3 |
| 극단 공포 반등 | 0 | 93 | 93 |

시점은 bar close+1h에 판단하도록 두었다. 가격 공개 지연 60초, 펀딩 300초, 심리지수 24시간은 **연구용 가정**이다. 2026년에 가져온 과거 데이터의 실제 당시 배포 기록이 아니다. 펀딩 최초 3 epochs는 24시간 창이 부족하다. 심리지수는 보수적으로 하루 늦게 쓰면서 36시간 freshness를 유지해 하루 후반 12시간이 차단된다. 이는 과거 공급자의 장애를 관측한 숫자가 아니다. 실제 배포·수신 시각으로 다시 실험해야 한다.

6개 unittest가 7종의 진입·청산과 결측·노후화·미래 revision·중복·잘못된 자산/공급자·수치·입력 순서·헤지 목표를 검증한다. **7종 전부 합성 계약 예제를 실행했지만, 실제 proprietary 데이터는 제공되거나 확보되지 않았다.** `custom-input.example.json`의 값은 합성이며 실데이터·성과로 표시하지 않는다.

실거래 0건, P&L 백테스트 0건, zkVM build/proof 0건, 플랫폼 업로드 0건이다. 이번 결과는 입력과 결정 함수 실행 검증이다. 83은 거래 횟수가 아니라 양의 목표가 나온 epoch 수다.

## 우리가 받아야 할 업로드 패키지와 다음 수용 시험

**제안 계약이며 현재 SDK 형식은 아니다.** `strategy artifact + parameter/schedule + asset/venue mapping + input schema + dataset/transform version + source authorization + timing/freshness policy + execution/risk policy + initial state + replay report`를 하나의 등록 commitment에 결박한다. Python 코드 hash만으로 데이터 생성 규칙이나 당시 가용성까지 고정되지는 않는다.

외부 데이터와 커스텀 피처는 세 경로로 구분한다.

1. 플랫폼이 수집·확정한 공개 원자료와 고정 변환: 펀딩·지수·공급량부터 지원한다.
2. 허용된 독립 공급자가 서명한 커스텀 피처: 신뢰 주체·방법론·버전·피처 범위를 공개한다. ZK의 명제는 그 입력에서 결정한 계산이다.
3. 제작자가 비밀 원자료/모델로 직접 피처 생성: 파이프라인 commitment와 원천 인증·실행 검증을 추가한다. 제작자의 무제한 임의 score를 받아놓고 전략 변경 불가라고 홍보하지 않는다.

가장 먼저 1번 펀딩 전략을 등록 후보로 삼고, 4번 순유출의 합성 계약을 입력 보안 시험으로 사용한다. 지연 입력·사후 revision·소스 바꿔치기·동일 epoch 중복·누락·부분 체결을 주입해 거절/실패 기록을 확인한다. 정상 TARGET(0 포함)와 DATA_BLOCKED를 구분해 기록해야 한다. 이후 실제 공급자 데이터를 붙여 shadow execution하고, proof 전체 지연과 비용을 측정한다.

수익성 판정은 별도다. 파라미터를 사전 고정하고 미사용 기간에 가격 단독 기준·현금·buy-and-hold와 비교하며, 거래 규모별 비용/슬리피지 민감도와 모든 실패·0진입 전략을 함께 남긴다. 이 7종만으로 거래 가능한 alpha가 검증되었다거나 외부 전략을 모두 올릴 수 있다고 결론 내릴 수 없다.
