# 구현 착수 판단 · 2026-09-20

**현재 선택한 기술로 통합 구현을 시작할 근거는 확보했습니다. 개별 TEE·DEX 실험을 반복하기보다, 다음 구현에서 전체 흐름을 연결하고 실패·복구를 검증합니다.** 실자금 운용이나 팀 명세 전체 인수를 승인한 것은 아닙니다.

## 이번에 추가로 확인한 것

[추가 검사 기록](evidence/zk-boundaries.json)의 로컬 회로 검사 30개를 통과했습니다. 두 Book 각각의 매수·매도 승인과 최소 수령량 정산 8개는 실제 R1CS 제약에 맞는 witness인지 확인했습니다. 다음 유형의 악의적 입력 22개는 witness 생성에서 거부됐습니다.

- 잘못된 전이 종류·Book 선택값·주문 방향
- 운용자 공개키 교체, 다른 Book의 제출 순서 변경·자산 생성
- 승인 단계에 미체결 수익 반영, 현금·자산 합계 조작
- 서명은 유효하지만 금액/최소 수령량이 0인 주문, 지출 한도보다 1단위 큰 주문
- 금액·만료·제출 순서의 96-bit 범위 초과
- 최소 수령량보다 1단위 적은 체결
- 정산하면서 예약을 남기거나 제출 순서를 증가시키는 변경
- 사전 확정한 Book·주문 금액 변경, pending commitment 없는 정산

변경된 사후 장부의 root도 다시 계산해 검사했습니다. 단순히 root 갱신을 빠뜨려 거부되는 것으로 검사를 통과시키지 않습니다. 새로운 TEE 실행·DEX 거래·Groth16 proof를 생성한 검사가 아니므로 기존 32개 포크 검사나 실제 TEE 결과와 구분합니다. 이 테스트가 임의의 악성 witness에 대한 회로 보안 감사나 수학적 완전성 증명은 아닙니다.

재현: `rtk proxy node scripts/verify-zk-boundaries.mjs`. 먼저 `rtk npm ci`와 `rtk npm run build:zk`가 필요합니다. 의도한 거부에서 나오는 `Error in template` 이후 최종 PASS와 종료 코드 0을 확인합니다. 비용이 발생하는 cloud 호출이나 외부 체인 송신은 없습니다.

## 다음 구현 단위와 종료 조건

첫 단위는 **암호화한 운용자 입력 → TEE 내부 장부·승인 proof → Vault/DEX 실행 → 실제 receipt → TEE 정산 proof → 확정 root**입니다. 처음에는 현재의 구체 주문·두 Book·현물 한 쌍을 유지합니다. 목표 포지션에서 주문을 도출하는 규칙은 그다음 별도 전이로 연결합니다.

1. 클라이언트는 서명된 주문만 보냅니다. 정상 운영 경로에서 전체 장부·witness를 호스트가 만들어 TEE로 넣지 않습니다.
2. TEE는 canonical root와 일치하는 자체 장부에서 승인 proof를 만들고, 동일 proof가 실제 연구 Vault 실행에 사용됩니다.
3. 정산은 relayer가 주장하는 수량이 아니라 승인된 체인의 Vault receipt와 일치해야 합니다. 가짜 receipt·중복·순서 변경은 거부합니다.
4. DEX 실패, 응답 유실, 체결 후 TEE 재시작을 주입합니다. 재시도해도 이중 체결·누락·다른 Book 전가가 없어야 합니다.
5. 과거 장부 snapshot을 복원했을 때 canonical root/cursor 불일치를 탐지하고, 최신 상태로 복구하기 전 다음 승인을 막아야 합니다. 암호화 저장만으로 rollback 방지가 완성되는 것은 아닙니다.
6. 위 연결은 로컬 시험을 먼저 통과시키고 실제 TEE에서 다시 확인합니다. 마지막에 Book별 장부 합계·예약·Vault 잔고·정산 cursor를 대조합니다.

이 작업의 완료 이후 입출금·지분·자기자본 잠금을 확장합니다. 성과 staking·보수율·최소 자기자본·평가 정책은 팀의 미확정 결정을 따라야 하며, 통합 구현을 시작하기 위해 임의로 정할 필요는 없습니다. 화면 작업은 이 상태와 증거를 조회하도록 뒤에 연결합니다.
