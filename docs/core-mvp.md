# 코어 MVP 검증 — 2026-09-23

## 이번에 답할 질문

운용자가 승인한 요청만 거래시키고, 요청량과 실제 체결량을 구분하며, 다른 Product의 자금을 건드리지 않고 포지션을 닫아 투자자에게 돌려줄 수 있는가?

두 Product A/B, Product마다 전용 계약 계정 하나, 투자자 한 명, BTC 시장 하나로 범위를 줄였다. 기존 v1.4/v0.1의 대체 명세나 전체 구현이 아니다. 전용 계정은 귀속 계산을 단순하게 하지만 Product와 거래 계정의 연결을 공개한다.

## 실제 경로

1. 테스트 투자자가 A/B 계약에 각각 AUSD를 넣는다. 계약이 Perpl 계정을 생성하고 정확한 금액만 승인한다.
2. 운용자가 목표 수량·한도가·nonce·기한·체인·계약·시장·현재 포지션·수량 한도·키를 묶어 서명한다.
3. ZK 경로는 서명과 수량 한도를 증명한다. TEE 경로는 서명된 입력을 암호화해 실제 TDX에서 같은 증명을 생성한다. 비밀키는 클라이언트에 남는다.
4. 거래 계약이 현재 포지션을 Perpl에서 직접 읽어 증명의 공개 입력을 구성한다. 허위 현재 포지션을 넣은 유효한 증명도 거절된다.
5. 계약이 IOC 주문을 조립하고 거래 후 실제 포지션을 다시 읽는다. 목표 수량을 체결 수량으로 저장하지 않는다.
6. 포지션이 0이고 잠금이 없으면 Perpl에서 담보를 꺼내 고정된 투자자 주소에 전달한다.

## 합격 기준과 증거

- A: 0→100 lot 매수, 목표 200이지만 미체결이면 100 유지, 추가 100 요청 중 25만 체결되면 125 기록, 실제 125를 기준으로 전량 축소·회수.
- B: A의 거래 전후 계정 상태 동일, 별도로 100 lot 매도·전량 축소·회수.
- 변조 요청, 다른 Product의 승인, 재사용, 한도 초과, 불리한 가격, 권한 없는 회수, 포지션 보유 중 회수, 중복 회수 거절.
- ZK: 서명 없는 입력 변조 5종, 허위 사전 상태 증명 거절. 실패 거래를 실제 로컬 블록에 채굴하여 nonce·자금이 변하지 않음을 확인.
- 모든 생성 증명을 다시 검증하고 모든 거래 영수증을 다시 조회한다.

[EIP-712 거래 증거](evidence/perpl-fork-mvp.json), [로컬 ZK 거래 증거](evidence/perpl-zk-mvp.json), [실제 TDX 연결 증거](evidence/perpl-tee-mvp.json). `transactions`는 로컬 포크 영수증이며 탐색기에서 찾을 수 없다. `observations`에서 목표·거래 전·거래 후 수량을 비교한다. `proofs`와 `verificationKey`는 공개 검증 자료다. `recoveries`는 투자자 지갑의 실제 수령액이며 수익성 평가가 아니다.

실행 결과: EIP-712 경로 22개 검사, 로컬 ZK 및 하드웨어 연결 경로 각각 30개 검사 통과. TDX 증명 8개는 약 3.06–3.49초/개였으며 통신·거래 대기시간을 제외한 단발 실측이다. 하드웨어 실행에서 A는 999.913719 AUSD, B는 999.930954 AUSD를 회수했다(각 1,000 AUSD 테스트 입금). 차액을 임의 보정하지 않았다.

## 재현

Node 22.23 이상, `npm ci`, 공개 Monad 테스트넷 RPC에 접근할 수 있어야 한다.

```sh
npm run prove:perpl
npm run build:perpl-zk
npm run prove:perpl:zk
npm run verify:perpl
```

러너는 Anvil을 loopback에 띄우고 실행 후 종료한다. 공개 RPC에는 읽기만 한다. `MM_PERPL_FORK_BLOCK`으로 블록을 고정할 수 있다. 오래된 블록은 제공자의 archive 지원이 필요하다. 결과는 `.data/perpl-mvp/latest.json`에 기록하며, 성공할 때만 `docs/evidence/` 결과를 갱신한다. 현재 호가 간격·유동성 조건이 맞지 않으면 실패하며 성공으로 간주하지 않는다.

`verify:perpl`은 저장된 9개 증명을 암호학적으로 재검증하고 6개 실행 관측값에 대응하는 증명이 있는지 확인한다. 오프라인 JSON 검사는 과거 영수증과 TEE 생성 출처를 독립 인증하지 않는다. 그 부분은 연결 실험을 다시 실행해야 한다.

### 실제 TEE 재현

1. ZK 산출물을 먼저 빌드한다. `npm run prepare:perpl:tee`가 `.data/perpl-tee-mvp/compose.yaml`과 접근 토큰이 든 `client.json`을 만든다. 파일은 커밋하지 않는다. 기존 실험 접근 권한을 유지하는 업데이트에는 `-- --reuse-access`를 쓴다.
2. 승인된 Phala 실험 VM에 Compose를 반영한다. **Save가 중지된 VM을 재시작할 수 있다.** 설정 파일의 SHA와 Phala deployment의 compose hash는 다르다. UI에서 해당 배포의 compose hash를 읽어 `client.json`의 `composeSha256`에 기록한다.
3. `MM_PERPL_TEE_ENDPOINT=https://<해당 VM의 ingress> npm run prove:perpl:tee`를 실행한다. 인증서 서명·새 challenge·암호화 키 결합·RTMR 이벤트·배포 해시·산출물 해시가 맞지 않으면 중단한다.
4. 완료 여부와 관계없이 Phala VM을 Shutdown하고 Stopped를 확인한다. 앱의 25분 자동 종료는 VM 과금 종료가 아니다. 기존 승인 상한 $2를 유지한다.

정상 요청 8개는 하드웨어에서 증명하고, 허위 사전 상태 반례 1개는 로컬에서 만든다. 입력 변조/수량 초과 검사는 로컬 witness 계산으로 거절을 확인한다. TEE는 20개 요청 상한, 클라이언트는 12개 상한이 있다. 재빌드하면 증명 키 해시가 바뀌므로 TEE 설정도 새로 배포해야 한다.

## 무엇을 검증하지 않았는가

- DEX는 실제 배포된 Perpl 바이트코드·상태를 복제한 **로컬 포크**다. 공개 테스트넷 배포·거래·실자금 운용이 아니다. 이 기록은 chain 31337 포크에서 생성했다. 9월 24일 후속 변경에서 10143의 지정된 테스트 venue도 제한적으로 허용했다.
- 로컬에서 Exchange를 impersonate하여 테스트 담보를 마련했다. 실제 faucet·자금 조달·거래소 지급능력 검증이 아니다. 부분 체결에는 로컬 maker의 25 lot 주문을 사용했다. 거래소 코드·매칭 규칙은 바꾸지 않았다.
- 포크에 오라클 업데이트가 없으므로 블록 시간을 동결했다. 실제 오라클 지연, 네트워크 지연, 재조직, 장시간 funding, 청산·출금 혼잡은 검증하지 않았다. 포크 gas는 Monad 실측 성능이 아니다.
- 전량 종료 후 회수 성공은 부분 축소의 DCP/비동기 증거금 해제까지 증명하지 않는다.
- 이 회로는 목표 승인·범위를 검증한다. Ledger transition, NAV, 지분 발행·소각, 보수, slot 임대, committee, forced exit는 미구현이다.
- TEE는 합성 입력의 암호화 수신·증명 생성만 수행한다. 실제 전략 엔진, 키 보관·갱신, TEE 내부 relayer, private 제출, 장기 복구는 미구현이다. 제출 전 목표도 로컬 클라이언트에서 생성한다. 모든 민감 데이터가 TEE에만 존재한다는 주장은 하지 않는다.
- 공개 입력에 목표·현재 수량·계정·키가 포함되므로 거래와 Product 귀속을 숨기지 않는다. TDX 인증은 vendor verification API 및 공급자 신뢰에 의존한다.
- Groth16은 로컬 단일 참여자 setup이다. 운영용 ceremony·감사·soundness 검토를 대체하지 않는다.

## 단일 트랜잭션 추가 검증

2026-09-23 `npm run prove:perpl:atomic` 통과: 총 32개 검사, 10개 증명, 성공 주문 6건의 내부 호출 추적. [원본 증거](evidence/perpl-atomic-mvp.json)의 `atomicity`에 call trace와 실패 전후 상태를 저장했다. 이번 추가 실행은 로컬 CPU 증명 + 로컬 Perpl 포크이며 기존 TDX 실행과 별도로 기록한다. 유료 VM을 재시작하지 않았다.

성공 거래에서는 같은 최상위 거래 안에서 verifier가 true를 반환한 다음 Perpl `execOrder`가 실행됨을 확인했다. 주문은 IOC이며 요청량은 목표와 실제 사전 포지션의 차이와 일치한다. 전량 회수 후 유효한 증명으로 신규 주문을 보냈을 때, 실제 Perpl 호출이 revert했고 nonce·A/B 계정·A 포지션·투자자 및 계약의 AUSD 잔액이 모두 이전 값과 같았다. 실패 거래의 가스는 소비되며 relayer의 가스 잔액까지 복원된다는 뜻은 아니다.

TEE의 입력 수신·증명 생성과 입금·거래·회수 전체가 하나의 거래라는 뜻은 아니다. 단일 거래 보장은 `execute` 안의 증명 검증→주문→실제 결과 확인에 한정된다.

```sh
npm run prove:perpl:atomic
npm run verify:perpl -- docs/evidence/perpl-atomic-mvp.json
```

[검토 시나리오](core-mvp-scenarios.md)를 통해 이 범위를 확인한다. 공개 Monad 테스트넷의 실제 체인 영수증과 오라클 갱신·네트워크 실패는 다음 검증 단계다.

공개 테스트넷 후속 준비는 [별도 기록](perpl-public-testnet.md)을 따른다. 9월 24일 변경 후 로컬 원자성 검사를 다시 통과했으며, 이전 하드웨어 실행은 당시 버전의 기록으로 보존한다.
